---------------------------------------------------------------------
ШАГ 0. ЧТО ТАКОЕ PWA (своими словами)
---------------------------------------------------------------------
PWA = обычный сайт, который:
  - можно установить как приложение (иконка на рабочем столе, своё окно);
  - открывается и работает без интернета;
  - нормально выглядит на телефоне.

Для этого нужны 3 вещи:
  1. manifest.json — "паспорт" приложения (имя, иконки, цвета);
  2. Service Worker — скрипт-посредник между страницей и сетью (кэш);
  3. HTTPS (на GitHub Pages он уже есть; localhost тоже считается безопасным).

ШАГ 2. КАК SERVICE WORKER ПОПАДАЕТ В СБОРКУ (vite.config.js)
---------------------------------------------------------------------
Проблема: после npm run build файлы называются по-разному каждый раз
(index-AbC123.js). А Service Worker должен знать ВСЕ файлы, чтобы
сохранить их в кэш при установке.

Решение: маленький свой плагин serviceWorkerPlugin в vite.config.js.
После сборки он:
  1) проходит по папке dist и собирает список файлов:
     ['./assets/index-AbC.js', './index.html', './offline.html', './icons/...', './']
  2) делает версию = время сборки, например 20261118144446176
  3) берёт шаблон sw/service-worker.js, подставляет версию и список
  4) сохраняет результат в dist/sw.js

Поэтому каждая новая сборка = новый sw.js = браузер видит обновление.

Почему не Workbox? Задание разрешает писать вручную. Так весь код у нас
перед глазами и его легко объяснить.

    navigator.serviceWorker.register('/react-autumn/task7/sw.js')

ШАГ 4. ЖИЗНЕННЫЙ ЦИКЛ: install -> waiting -> activate
---------------------------------------------------------------------
Файл: sw/service-worker.js

4.1 INSTALL — первая установка или новая версия
    caches.open('shell-<версия>').then(cache => cache.addAll(PRECACHE_FILES))
  Скачиваем и сохраняем ОБОЛОЧКУ приложения (app shell):
  index.html, все JS и CSS, иконки, manifest.json, offline.html.
  Если хоть один файл не скачался — установка не удаётся (так безопаснее).

  ВАЖНО: в install нет self.skipWaiting().
  Новая версия ставится в состояние "waiting" и ждёт разрешения.

4.2 ACTIVATE — новая версия стала главной
  - caches.keys() -> удаляем все кэши, которых нет в CURRENT_CACHES
    (например, shell-20261118144239595 от прошлой версии);
  - self.clients.claim() -> сразу управляем открытыми вкладками.

4.3 FETCH — каждый запрос страницы проходит через Service Worker
  (подробно в шаге 6).

4.4 MESSAGE — приложение может прислать { type: 'SKIP_WAITING' }
  -> self.skipWaiting() -> ждущая версия активируется.


---------------------------------------------------------------------
ШАГ 5. ОБНОВЛЕНИЕ ПРИЛОЖЕНИЯ (баннер "Update now")
---------------------------------------------------------------------
Сценарий: мы задеплоили новую версию, а у пользователя открыт старый сайт.

1. Браузер сам проверяет sw.js при открытии страницы
   (+ мы вызываем registration.update() раз в 30 минут).
2. sw.js изменился (другая версия) -> новый worker делает install.
3. В приложении срабатывает 'updatefound' -> 'statechange' -> 'installed'.
   Если при этом уже есть controller (старая версия) — это ОБНОВЛЕНИЕ.
4. Показываем UpdateBanner: "A new version of the app is available"
   [Update now] [Later].
5. Update now -> activateUpdate() -> registration.waiting.postMessage({type:'SKIP_WAITING'})
6. Новый worker активируется -> удаляет старый кэш.
7. В приложении событие 'controllerchange' -> window.location.reload()
   (один раз, флаг reloaded) -> загружаются новые JS/CSS.

Итог: пользователю НЕ нужно чистить кэш вручную.

Почему не обновлять сразу (skipWaiting в install)? Тогда старая страница
могла бы попросить старый файл, которого уже нет в новом кэше, и сломаться.
Поэтому спрашиваем пользователя.


---------------------------------------------------------------------
ШАГ 6. FETCH И СТРАТЕГИИ КЭШИРОВАНИЯ
---------------------------------------------------------------------
Порядок проверок в обработчике fetch:

  1) Не GET (POST, PUT, DELETE) -> не трогаем, идёт в сеть.
  2) googleapis.com, firebaseapp.com, google.com, gstatic.com -> не трогаем.
     Это Firebase Auth: токены и данные пользователя НЕЛЬЗЯ класть в общий кэш.
  3) Навигация (request.mode === 'navigate') -> handleNavigation
  4) openlibrary.org -> networkFirst (API)
  5) Картинки (request.destination === 'image', covers.openlibrary.org) -> cacheFirst
  6) Свои файлы (тот же origin) -> сначала кэш оболочки, потом сеть

СТРАТЕГИЯ 1. CACHE-FIRST (картинки, обложки, иконки)
    есть в кэше? -> отдаём СРАЗУ (без сети)
    нет -> fetch -> сохраняем в 'images-v1' -> отдаём
    нет сети и нет в кэше -> пустой ответ 503 (картинка не покажется, но ничего не сломается)
  Почему: картинки не меняются, а грузятся долго. Из кэша — мгновенно.
  status 0 — это "opaque" ответ (картинка с другого сайта), его тоже можно хранить.

СТРАТЕГИЯ 2. NETWORK-FIRST (API Open Library: список и детали)
    пробуем сеть -> получилось -> сохраняем копию в 'api-v1'
                    (+ заголовок X-Cached-At = когда сохранили) -> отдаём
    сеть упала   -> ищем в кэше:
                    есть и не старше 1 дня -> отдаём, добавив в JSON
                       _fromCache: true, _cachedAt: <время>
                    нет -> отдаём { error: 'offline' } со статусом 503
  Почему: данные API могут меняться, поэтому сначала пробуем свежие.
  Кэш — запасной вариант на случай, когда нет сети.

НАВИГАЦИЯ (handleNavigation)
    сеть -> обычный ответ
    нет сети:
      адрес приложения (/task7/ или /task7/index.html) -> index.html из кэша
          (приложение откроется, все страницы через #/ работают)
      любой другой адрес -> offline.html из кэша

Мелкая, но важная деталь — ignoreVary: true.
Сервер присылает заголовок "Vary: Origin". Скрипты с атрибутом crossorigin
отправляют заголовок Origin, а файлы в кэш мы клали без него. Из-за этого
caches.match "не узнавал" файл, и без сети была белая страница.
{ ignoreVary: true } говорит кэшу не смотреть на Vary.
(Нашли эту ошибку при тестировании.)


---------------------------------------------------------------------
ШАГ 7. ОГРАНИЧЕНИЕ РАЗМЕРА КЭША
---------------------------------------------------------------------
Кэш не должен расти бесконечно.
  images-v1 : максимум 60 записей
  api-v1    : максимум 50 записей + срок жизни 1 день (API_MAX_AGE_MS)
  shell-... : при каждой новой версии старый удаляется в activate

Функция trimCache(cacheName, maxEntries):
  cache.keys() отдаёт записи в порядке добавления -> удаляем самые старые,
  пока их не станет maxEntries.

---------------------------------------------------------------------
Наш "API" книг из прошлых заданий — fake API в localStorage. Через сеть
он не ходит, поэтому Service Worker его не видит. Для runtime-кэширования
нужен настоящий сетевой API, поэтому добавили Open Library:

  /discover?q=tolkien&page=2   -> СПИСОК    GET https://openlibrary.org/search.json?q=...
  /discover/OL27482W          -> ДЕТАЛИ    GET https://openlibrary.org/works/OL27482W.json
  обложки                     ->           https://covers.openlibrary.org/b/id/<id>-M.jpg

Файлы:
  src/services/openLibrary.js  — функции searchBooks, getWork, coverUrl
                                 + понимает _fromCache из ответа SW
  src/hooks/useOpenLibrary.js  — useSearchBooks, useWork (TanStack Query)
  src/pages/DiscoverPage.jsx, DiscoverDetailsPage.jsx

Если данные пришли из кэша SW -> показываем CachedNotice:
  "💾 You are viewing cached data (saved 19:41). It will update when the connection returns."

API публичный, без входа -> его можно хранить в общем кэше.

ШАГ 9. ОФЛАЙН-СТРАНИЦА И ИНДИКАТОР
---------------------------------------------------------------------
Офлайн-страниц две, и у каждой своя задача:

1) public/offline.html — статический файл, лежит в кэше SW с момента установки.
   Его отдаёт Service Worker, когда нельзя открыть страницу (не приложение).
   Все стили внутри файла -> работает без единого запроса в сеть.

2) Маршрут /offline (src/pages/OfflinePage.jsx) — та же страница внутри React.
   Её же показываем на Discover, если без интернета открыли поиск или книгу,
   которых нет в кэше ("навигацию нельзя выполнить офлайн").

Кнопка "Retry connection":
  Делаем НАСТОЯЩИЙ запрос: fetch('manifest.json?check=<время>', {cache:'no-store'}).
  ?check=... нужен, чтобы ответ не взялся из кэша SW.
  Получилось -> возвращаемся/перезагружаем данные. Нет -> "Still offline".
  (navigator.onLine иногда врёт: Wi-Fi есть, а интернета нет.)

Индикатор:
  useOnlineStatus() слушает события window 'online' / 'offline'.
  OnlineIndicator в шапке: зелёный "Online" / красный "Offline".
  OfflineBar: красная полоса под шапкой, пока нет сети.
  Когда сеть вернулась -> индикатор зелёный, TanStack Query сам перезапрашивает
  данные (refetchOnReconnect), CachedNotice пропадает.

ВОЗМОЖНЫЕ ВОПРОСЫ НА ЗАЩИТЕ
---------------------------------------------------------------------
В: Что такое Service Worker?
О: JS-файл, который браузер запускает отдельно от страницы. Он перехватывает
   все запросы (fetch) и решает: взять ответ из кэша или из сети. Нет доступа
   к DOM. Работает только по HTTPS или на localhost.

В: Чем cache-first отличается от network-first?
О: Cache-first: сначала кэш, сеть только если нет в кэше (быстро, для
   неизменных файлов — картинок). Network-first: сначала сеть, кэш только
   если сеть упала (свежие данные, для API).

В: Зачем версия в имени кэша?
О: Новая сборка = новый кэш shell-<версия>. В activate удаляем старые.
   Так пользователь получает новые файлы, а старые не копятся.

В: Что такое waiting и skipWaiting?
О: Новый SW после install ждёт, пока закроются все вкладки со старой
   версией. skipWaiting() — "не ждать, активироваться сейчас". Мы вызываем
   его только по кнопке Update now.

В: Почему не кэшируем запросы Firebase?
О: Там токены и личные данные пользователя. В общем кэше их мог бы увидеть
   другой пользователь этого браузера, или отдались бы устаревшие токены.

В: Как ограничен размер кэша?
О: images — 60 записей, api — 50 записей и 1 день, shell заменяется при
   каждой версии. trimCache удаляет самые старые записи.

В: Почему navigator.onLine недостаточно?
О: Он показывает только, подключено ли устройство к сети (Wi-Fi), а не
   есть ли интернет. Поэтому Retry делает реальный запрос, а офлайн-страница
   лежит в кэше SW и открывается вообще без сети.

В: Почему в dev-режиме нет Service Worker?
О: Vite в dev отдаёт файлы по-другому (без сборки), и SW закэшировал бы
   старый код. Тестируем через npm run build + npm run preview.
